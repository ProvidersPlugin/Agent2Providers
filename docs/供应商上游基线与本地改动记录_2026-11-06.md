# 供应商上游基线与本地改动记录

记录时间：2026-11-06
范围：ZCode、AutoClaw、OfficeAce（果办）三家在 2026-11-05 至 2026-11-06 的故障排查结论、上游接口基线实测与本地代码改动，另附 trae 工具声明警告的归因

## 一、ZCode

### 上游基线实测（2026-11-06 凌晨，接口域名 https://zcode.z.ai）

- 套餐探测接口 `/api/v1/zcode-plan/billing/preview`：
  - 匿名请求（无 Authorization）返回 HTTP 401 空响应体，带 WAF Cookie 二次握手仍 401，判定上游已关闭匿名访问
  - 携带账号 JWT 返回 HTTP 200 且业务码为 0，四个账号（国内版与国际版）登录态全部有效
- 营销接口 `/api/v1/marketing/touch` 携带 JWT 返回 200，`deliveries` 为空
- 客户端版本门槛：`app_version` 3.18.0 至 3.21.0 探测到的 `plans` 均为空，连续探测 3.22.0 起触发 429，版本号不是空列表的原因
- 当日赠送套餐北京时间 19:00 起可领，活动期上游每天下发 `zcode-v3-start-plan-<日期>` 形态的套餐
- 领取动作上游强制人机验证（阿里云验证码，官方 SDK 求解）：19:01 定时领取四个账号全部失败，失败原文为「需要人工验证：没有可用的验证界面」；实测手动领取无滑块弹窗，验证基本无感通过

### 故障定位

- 「ZCode 匿名目录未完成：登录态已失效，无法探测套餐」：匿名目录探测本就不携带凭证，401 是上游关闭匿名访问所致，报错文案误导
- 自动领取失败的原因：面板页在浏览器形态（`platform === 'web'`）且 `document.visibilityState` 非 visible 时主动把验证客户端标记为不就绪（A2API 仓库 `ui/zcode-claim-verification.js` 的 `canVerify`），且浏览器对后台标签页的定时器节流使 5 秒心跳撑不住插件侧 40 秒客户端有效期，调度端因此报「没有可用的验证界面」

### 本地改动（本轮）

- A2API 仓库 `desktop-tauri/ui/zcode-claim-verification.js`：取消浏览器形态的前台可见性门槛，并增加 Worker 心跳通道，后台标签页也能按 5 秒节奏接验证任务（详见「五、本地改动清单」）

## 二、AutoClaw

### 上游基线

- 刷新链路：`POST /userapi/v1/refresh`（签名头 `X-Auth-Sign = MD5(appId&ts&appKey)`），业务码 400002 时降级 `POST /userapi/v1/agent-refresh` 再试
- 访问令牌为 24 小时有效期；插件每小时无条件强制刷新一次，用于温着会被服务端轮换的 refresh_token
- 回写口径：插件 `persist_refresh` 同时写两套键（`token` / `tokenExpiresAt` 与 `accessToken` / `expiresAt`），写前做比较再写
- 实测两个账号库存的 `token` 与 `refreshToken` 均带 `Bearer ` 前缀（总长 382 / 383，含 7 字符前缀）

### 故障定位与本地改动

- 现象：凭证刷新报「账号……的凭证刷新未产生变化（适配器报成功但凭据未更新）」（A2API 仓库 `credential_maintenance.rs` 的 `refresh_checked` 指纹核对）
- 根因：`persist_refresh` 回写前用「剥过前缀的凭证快照」与「库里带前缀的原值」比较，恒不相等，被误判为「凭证已被别处换过」，于是跳过回写并把旧令牌按成功返回；主仓指纹未推进即报错。刷新本身可能已在上游成功，但结果被整体丢弃
- 修复：比较与兜底读取两侧统一先剥前缀（Agent2Providers 仓库 `crates/providers/src/providers/autoclaw/mod.rs`）；`cargo check -p agent2api-providers` 通过，无新增告警
- 残余观察点：若上游在令牌有效期内始终原样返回旧值（不轮换），每小时强刷仍会在主仓指纹核对处报「未产生变化」，需在令牌到期窗口（2026-11-06 08:40）实测确认上游是否真轮换

## 三、OfficeAce（果办）

### 上游基线实测（2026-11-06）

- 两层凭据：网关 Basic（转发用，不过期）与控制面临时 AK/SK + securityToken（约 2 小时有效期，DPoP + refresh_token 续期链路实测正常，到期前 30 分钟插件自动续期）
- `GET /v1/subscription`（V11 签名）返回 200，凭据有效；`subscribe_status` 为 `UNSUBSCRIBED`
- `POST /v1/subscription/bonus/claim` 返回 403，错误码 `OfficeAce.11020604`「未订购套餐」；账本中唯一的「新用户专属福利」4000/4000 已全额到账，无可领奖励
- 插件把一切 401/403 统一报「控制面凭据已失效（临时 AK/SK 会过期）：请重新登录一次」（`officeace/subscription.rs`），403 业务拒绝被误归因为凭据失效
- 匿名路径探测不可行：modelgw 网关在鉴权层统一拦截，不存在路径与存在路径同样回 401 `APIG.0303`，仅已知 IAM 签名接口（`/v1/subscription`、`/v1/model-token-rates`）回 `APIG.0301`；云侧 agentarts 网关对不存在路径回 404 `APIGW.0101`，可作为方法级探测依据
- 微信小程序「果办」另有独立签到入口（账号 139****4895 签到成功），API 形态未知；modelgw 鉴权前置导致匿名枚举不可用，需要抓包确认接口与鉴权形态

### 错误归因修正（2026-11-06 已实施）

- 403 业务拒绝归为中性提示（携带上游 `error_msg` 与 `error_code`，如「未订购套餐（OfficeAce.11020604）」），不再报「凭据已失效请重新登录」
- 401（`APIG.0301` 与 `0303` 一族，鉴权被拒）挂续期标记，由 `control::claim_bonus` 换新凭据重试一次；安全令牌过期文案（`APIG.0602` 配过期文案、`APIG.1002`）维持原有续期口径

### PC 客户端签到与领取逻辑（2026-11-06，本机 1.4.1 安装目录实证）

- 安装形态：Electron 应用（`%LOCALAPPDATA%\Programs\OfficeAce`），主逻辑在 `resources/app.asar` 与未打包的 `packages/api/dist/`（本地服务）
- 签到调度：渲染层每小时整点去重触发一次，另监听主进程转发的 `system-resume`（OS 唤醒）做「签到积分补领」
- 领取链路：渲染层 `POST /api/subscription/claim-bonus`（相对路径，打本地服务）→ 本地服务 `claimBonus()` → 云端 `POST /v1/subscription/bonus/claim`（与网关完全同路径同参数）；`baseUrl` 由 `resolveModelApigOrigin` 按用户解析到各自的 modelgw 源（与本机账号库里的 `modelgw-0009.…` 同族）
- 凭据与签名：本地服务会话持「signed」形态凭据（AK/SK + securityToken + projectId），`cloudFetch` 以 v5/v3 双凭据签名，与网关插件同一套体系
- 活动常量：`bonus-daily-checkin-2026`（每日签到）、`bonus-nationalday-checkin-2026`；领取失败（非 2xx）静默返回空数组，UI 无感
- 结论：PC 客户端、微信小程序、网关三方是**同一个订阅池、同一个业务动作**，不存在客户端独有的可白嫖接口；「未订购套餐」的结算门槛三方一致，`bonus-daily-checkin-2026` 每日签到只对已订购账号结算（`bonus_skus` 是已发放账本，未发放不出现在账本里）

### 客户端「0 元试用包」自动开通链路（2026-11-06，新版安装目录实证）

- 探测期间客户端自更新重装了一次（安装目录短暂被替换），新版代码包布局一致，以下结论来自新包
- 试用编排（本地服务）：`GET /api/codeagent-package/trial-status` 查状态、`POST /api/codeagent-package/ensure-trial` 开通（body 须 `agreedToTerms:true`，缺了回 `CODEAGENT_AGREEMENT_REQUIRED`）
- 云端实现（CodeArts 控制台域，不是 OfficeAce 域）：

  - 开通：`POST https://devcloudconsole.cn-north-4.myhuaweicloud.com/v5/orders/subscribe`，body `order_infos[0]`：`is_auto_pay:"yes"`、`subscription_num:1`、`period_num:1`、`period_type:2`、`is_auto_renew:"yes"`、`product_id:"OFFI1298576195589636096"`、`resource_spec_code:"codearts.agent.individual.trial"`、`cloud_service_type:"hws.service.type.devcloud"`、`resource_type:"hws.resource.type.codearts.snap"`；头 `x-target-services: codearts-console-iam5`；区域 `cn-north-4`

### 复刻实验结果（2026-11-06，JoyceWeng 账号，经 NAS 数据目录取凭据实测）

- Docker 网关（NAS 上的容器数据目录）侧凭据新鲜有效（JoyceWeng 在 Docker 网关的账号 id 为 `officeace-account-22574a2a…`，凭据至 10:02），`GET /v1/subscription` 返回 200，`subscribe_status` 仍为 `UNSUBSCRIBED`

- 复刻 `POST /v5/orders/subscribe` 被 CodeArts 控制台前的 CloudWAF 以 400 HTML 直接拦截（V11 与 SDK-HMAC-SHA256 两种签名、`/DevCloudConsole` 路径前缀、Cookie 会话、keep-alive 等组合均试过），请求未到应用层；客户端的 undici 栈能通过，疑与 TLS 指纹或 WAF 会话挑战相关，自动化复刻需要继续逆向 WAF 放行条件，成本高收益存疑

### 微信小程序「果办」接口面还原（2026-11-06，解包 wxapkg 实证）

- 代码包：微信 4.x PC 端小程序包落在 `%APPDATA%\Tencent\xwechat\radium\users\<用户哈希>\applet\packages\<小程序 appid>\`（appid 此处不记录全文），`V1MMWX` 加密；算法为 AES-256-CBC（密钥 = PBKDF2-HMAC-SHA1(appid, "saltiest"，1000 轮，32 字节)，IV = `"the iv: 16 bytes"`，密文段 1023 字节）+ 其后 1 字节标记 + 余量按 appid 倒数第二字符异或；容器头与旧版不同（`0xBE` + 8 字节索引长 + 4 字节正文长 + `0xED` + 4 字节文件数）。三个包全部解开，密钥只由 appid 派生，不涉及用户隐私
- 业务主机：正式 `https://officeace.chat.huaweicloud-agentarts.com`，灰度 `officeace-gray.chat.huaweicloud-agentarts.com`；业务前缀 `/v1/appapi`
- 登录链路（无鉴权面 `/v1/wx-login/` 与 `/v1/appapi/auth/callback`）：
  1. `wx.login()` 取 code → `POST /v1/wx-login/auth/login`（body `{code}`）→ 返回 `auth_token`（临时态，以 `Bearer` 使用）
  2. `POST /v1/wx-login/huawei-login-url`（body `{phone_code}`，手机号短信）→ 返回 `authorize_url` 与 `session_id`，进华为云 OAuth
  3. `POST /v1/appapi/auth/callback` 完成回调，落 `account_profile.credential`
- 业务鉴权头：`Authorization: OfficeAceToken <credential>`（临时态为 `Bearer <auth_token>`）；另有 `X-Application-Id`、`X-Chat-User-Id`、`x-apig-appcode`（当前构建为空）

- 端点清单（`/v1/appapi/*`）：agreements（含 batch-sign / cancel-sign）、chats、devices、feedback/upload-url、intelligence（prompt-polish、rasr/short-stream）、memory（configuration、governance-statistics、pc-threads、search、user-profile）、org-agents、org-models、org-skills、push-subscriptions、schedule-tasks（含 executions）、session/logout、auth/callback、subscription（含 bonus/claim、usage/detail）；另有 `/v1/privateapi/applications/<id>/users/<id>`
- 结论：小程序「签到成功」与网关签到是同一业务动作；账号 139****4895 的成功应为其新用户奖励的一次性结算（与存量两账号已领的「新用户专属福利」4000 分同形），未订购套餐的结算门槛两边一致。接入价值有限：网关已有同一动作的 IAM 签名链路，差异只在鉴权面与主机

## 四、trae 工具声明警告归因

## 五、Qoder 国际版无法签到（2026-11-06 实测结论）

- 现象：Docker 网关（NAS）上 `qoder-intl` 每日签到返回「该账号今天没有可领取的每日积分活动（上游未下发，与本机环境无关）」，中国版正常（「今日已领取」）
- 接口对照（真实账号令牌 `mojie126@foxmail.com`，`GET https://openapi.qoder.sh/sash/api/v1/me/campaigns?forceRefresh=true`）：
  - 不带风控头：只有 `VIEW_DETAILS` 促销活动
  - 带 **Docker 内 UMID 组件**（`/data/plugins/agent2api-providers/qoder-umid/runtime-info`，env 4）生成的头：同样只有 `VIEW_DETAILS`，无积分活动
  - 带 **本机桌面客户端**（`Qoder CN\resources\umid\runtime-info.exe`，env 4）生成的头：立刻出现 `CLAIM_BENEFIT CLAIMABLE act-20261102-999`（100 credits）
- 差异点：两份组件自报的环境指纹不同，`vmInfo` 分别是 `{"isVm":true,"brand":"Docker","percentage":90}` 与 `{"isVm":true,"brand":"Hyper-V","percentage":77}`；上游设备风控把 Docker 环境判为高风险，不向该设备下发每日积分活动
- 结论：不是接口路径、鉴权或凭证问题，而是**运行环境指纹**问题。插件里「国际版需要 UMID 组件」的判定本身正确，缺的是「组件产出的身份必须来自非 Docker 环境」这一前提
- 可行的绕过方向（均需评估风险）：在 Docker 容器内伪造组件自报的 `vmInfo`（如覆盖为 Hyper-V）、挂载宿主机的 UMID 组件产物、或用真实桌面客户端的身份定期喂给网关；直接改上游风控判定不可行

### 深挖修正（2026-11-07，官方客户端抓包 + 新老账号对照实测）

- 11月6日的「Docker 高风险」结论**不完整**：用户澄清老账号 11月3-5 领取「每日登录」+100 时**从未安装过客户端、也未在客户端登录过**，因此「活动绑定客户端登录」的前提不成立，「每日登录」的实际发放渠道至今未定位
- 实测矩阵（新注册账号做活体对照，该账号在官方客户端登录过）：同一时刻同一账号，携带客户端机器 UMID 三件套（`cosy-machinetoken` / `cosy-machinecode` / `cosy-machinetype`）的请求能看到可领取的每日活动（`act-20261102-087`，网关路径实测 `POST …/claim` 返回 `CLAIMED` +100），携带网关 Docker 身份的请求看不到；令牌族（`jt-` / `dt-`）、`referer` / UA / `cosy-version` / `accept`、`cosy-machineid` 与主机名 / OS 均无关
- 老账号（`mojie126@foxmail.com`）：11月6 起被上游移出受众 —— 客户端身份、网关 Docker 身份、无机器头、匿名浏览器与网关网页重新登录（均留下会话记录）之后依旧无每日活动行，属账号级定向排除，疑与网关高频调用相关
- 已领取的每日活动行会全局可见（任何身份 / 无机器头都显示 CLAIMED），「CLAIMABLE 可领状态」才按身份门控；`deviceToken/poll` → `me/jobToken` 登录链路不带任何机器头，活动列表里已领取的行也不消失
- 按用户决定：**撤销**基于「绑定登录设备身份」的插件改动（账号 JSON 三件套字段与签到优先逻辑），维持官方 beta 合并后的既有 Qoder 优化；「每日登录」发放渠道留待后续观察（官方风控按账号定向，恢复 / 排除均由上游决定）

警告原文：`剔除原生（服务端执行）工具声明 1 条：web_search（本上游只承载 type:"function" 的函数工具）；provider=trae`

- 出处：A2API 仓库 `core/upstream/payload.rs` 出站处理的第 ④ 层「原生（服务端执行）工具声明闸门」，明细逻辑在 `core/protocol/native_tool.rs`
- 触发条件：客户端请求的工具声明里带了协议私有的服务端执行工具（Responses 协议的 `{"type":"web_search"}` 或 Anthropic 协议的 `web_search_20250305` 这类，常见于客户端开启了自带联网搜索），而 trae 上游只承载 `type:"function"` 的函数工具，上游对原生工具的处理是静默剔除（同类声明发给 CatPaw 则是整轮 400）
- 处置行为：网关出站前统一剔除并留痕，属于按设计的降级，不是错误；被剔除的只有服务端搜索声明，客户端声明的函数工具不受影响。若确认某家上游支持某类原生工具，可在该闸门按家按类型开白
